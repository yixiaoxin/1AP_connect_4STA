# AP 四 STA / UDP 重构说明

## 范围与状态

本次修改 AP 项目，支持 client_id 1、2、3、4。USB 仍为 48 kHz、16 bit、立体声；四个 STA 的立体声录音经四路自动混音输出为一个 USB 立体声流，并非把 USB 描述符改为八声道。

核心代码位于 `user/src/pub/demo_src.c`，UDP 分片定义位于同目录 `uac_udp_transport.h`。原有 BPK2 压缩、解压 CRC、录音抖动缓冲、补偿和采样时钟漂移校正继续使用。播放相同 PCM 的设备共享一次压缩结果；各设备拥有独立帧头、发送进度、录音状态、VAD 和增益。混音以 64 位累加，平滑后的 Q15 增益总和限制在 32768，避免四路叠加溢出；无活动语音但存在有效输入时保留平均混音。

**旧 TCP STA 固件不能直接连接新版 AP 音频服务。当前工作区没有提供待改造的 STA 应用，STA 必须按下述协议同步修改。** 仓库中的其他 TCP 功能（例如调试/IPERF）保留，音频业务已使用 UDP。

已完成主机单元测试和 SDK 头文件语法检查；未完成 ARM 固件完整链接、烧录及四设备射频联调。现存 `build/` 内 ELF/BIN/MAP 是旧产物，不代表本次修改已经构建成功。

## UDP 协议

AP 地址沿用 `192.168.88.1`。UDP 8888 是播放服务，UDP 8890 是录音服务，各由一个任务独占 socket。四个设备共用这两个服务端 socket，单个设备掉线不关闭共享 socket。

### 注册和状态同步

STA 为两个方向分别创建并保持一个 UDP socket，从该 socket 定期发送一个完整的 25 字节 HELLO 数据报到对应 AP 端口。所有多字节整数均为**小端**，结构体无填充，沿用既有音频头：

| 音频头字段 | 字节数 | HELLO 取值 |
|---|---:|---|
| magic | 4 | `0xA55A5AA5` |
| seq_num | 4 | HELLO 可固定为 0，与录音音频序号独立 |
| timestamp | 8 | 非零会话 token；同一 socket 的重复 HELLO 保持不变，重建会话时更换 |
| packet_type | 1 | `0x02` |
| direction | 1 | 向 8888 注册填 1；向 8890 注册填 2 |
| client_id | 1 | 1～4，每台设备唯一 |
| data_len | 2 | 4 |

后接 4 字节控制载荷：`ctrl_type=0x10, value=client_id, reserved=0`（reserved 为 16 位）。AP 原样回送 HELLO 作为 ACK。STA 建议每 1 秒重复发送，即使录音或播放未开启也继续发送；首次发送丢失后重试，收到录音端 ACK 后才发送录音音频。

AP 将每个方向的 ID 与源 IP、源端口、token 绑定。存活期间拒绝其他端点或 token 抢占同一 ID；3 秒没有有效 HELLO 则释放该方向并清空其缓冲。相同端点/token 的重复 HELLO 不重置序号和抖动缓冲。设备重启更换 token 后最多等待 3 秒重新注册。此绑定用于会话隔离，不是加密认证。

AP 的控制下行也是完整 25 字节数据报，无分片封装：`direction=1, packet_type=0x02`；`ctrl_type=0x04` 的 value 表示 USB 麦克风开关。每次有效播放 HELLO 都触发当前开关状态重发。`ctrl_type=0x05` 是空闲心跳，value 同样携带当前麦克风状态。STA 应幂等更新状态，不对这些控制包再发 ACK。HELLO ACK 通过 ctrl_type=0x10 区分。

### 音频分片

音频帧仍由原 21 字节头和载荷组成。播放使用 10 ms / 1920 字节 PCM，压缩成功时 type=0x04，否则 type=0x03 原始 PCM。录音也支持这两种 10 ms 格式；type=0x05 的 REC20 组保持旧格式，但**含组头的载荷必须不超过 1920 字节**，超限时 STA 必须回退为两个独立 10 ms 帧。初次 UDP 联调建议固定发送 10 ms 帧。

每个完整音频帧最多 1941 字节，按 1000 字节切片，每片增加以下 16 字节 ADU1 头：

| 分片字段 | 字节数 | 含义 |
|---|---:|---|
| magic | 4 | `0x31554441` |
| seq | 4 | 与内层 audio_header.seq_num 相同 |
| total | 2 | 完整内层帧长度，21～1941 |
| offset | 2 | 0 或 1000 |
| client_id | 1 | 1～4，与内层一致 |
| direction | 1 | 播放 1，录音 2，与内层一致 |
| reserved | 2 | 0 |

片载荷长度严格等于 `min(1000, total-offset)`。最大 UDP 载荷 1016 字节（加 IPv4/UDP 头为 1044 字节），无需依赖常见 1500 MTU 的 IP 分片。控制包与音频片应先按 magic 区分，不能只按数据报长度区分。

每设备保留一个重组槽，允许同一帧两个分片交换到达顺序；重复片不重复解码。首片到达后超过 30 ms 的残帧丢弃；新序号替换未完成旧帧，后到的旧帧丢弃，不做跨帧排序等待。32 位序号按模运算比较，支持回绕；跳跃应小于半个序号空间，重启通过新会话注册重置。

录音音频序号每个内层音频帧递增 1，HELLO 不消耗该序号。AP 继续根据序号缺口补偿；若混用 REC20 与 10 ms 帧，丢失时长仍按收到帧的类型近似估计，精确时长要求固定帧周期。压缩帧经既有 CRC 校验；原始 PCM 没有新增应用层 CRC。

播放发送暂时遇到 EAGAIN/ENOMEM 时短暂重试，20 ms 无发送进展丢弃待发帧，下一序号暴露缺口。发送成功仅表示交给网络栈，不代表 STA 已收到。不要按 TCP 字节流方式拼接 UDP 数据报，也不要重传半帧剩余字节形成无头数据报。

## 缓冲与内存

| PCM 缓冲 | 原两路版本 | 四路版本 |
|---|---:|---:|
| USB speaker | 2880 B / 15 ms | 2880 B / 15 ms |
| 每 STA 播放 | 1920 B / 10 ms | 1920 B / 10 ms |
| 每 STA 录音 | 3840 B / 20 ms | 7680 B / 40 ms |
| USB microphone | 1920 B / 10 ms | 1920 B / 10 ms |
| PCM 环总量 | 16320 B | 43200 B |

录音启动预缓冲 15 ms，超过 35 ms 时裁剪保留最新 20 ms。容量增加用于吸收突发，不代表总端到端延迟恒为 40 ms。

四路 session、播放环和录音环整合为启动时一次性分配的池，运行中不按包动态申请音频缓存。32 位指针、8 字节双字对齐的主机布局检查得到：session 4248 B，池 55392 B。该结果用于预算，最终值以目标编译器和开机 `UACM MEM pool=` 为准。USB 两个缓冲仍占静态内存 4800 B。相对原源码，预计减少约 19.4 KiB 静态 DRAM，占用转入独立堆。

FreeRTOS `rtos_task_create` 的 stack_depth 直接传给 `xTaskCreate`，单位是 32 位字：播放 4096×4=16384 B，录音 16384 B，混音 2560×4=10240 B，共 43008 B。混音局部 PCM 数组从三块增为五块，共 4800 B，仍在已有 10 KiB 混音任务栈内；嵌套调用、编译优化影响实际栈峰值，必须上板测水位。

启动申请池前要求剩余堆至少为：`sizeof(pool) + 43008 + 32768`，当前预算 131168 B。额外 32 KiB 是任务控制块、互斥量、网络及后续分配的预留目标，不是最坏情况证明。分配、互斥量创建或任务创建失败会停止音频启动；三个 worker 全部创建成功后才释放启动门。每 10 秒打印总堆、当前剩余和历史最小剩余。

### 链接区域核查

推荐 profile 使用 `map_cm4_combo.txt` 的非 FLASH_FW、非 DPD 分支：

| 区域 | 地址范围（尾地址不含） | 容量 |
|---|---|---:|
| DRAM | 0x001BFA00～0x001D8000 | 99840 B |
| D_HEAP | 0x00110000～0x00160000 | 320 KiB |
| 原 .heap | 0x00110000～0x00140000 | 192 KiB |
| 四路 profile .heap | 0x00110000～0x00150000 | 256 KiB |

新 profile 的 .heap 增加 64 KiB，但未扩大物理 MEMORY 区域、未挪动 Wi-Fi 固件、IPC、RX pool 或 BT patch，D_HEAP 尾部还保留 64 KiB 未纳入 FreeRTOS 堆。

仓库原 host-wb `linkinfo.armgcc_4_8.txt` 中 `.uninited` 结束于 0x001D7E28，主栈下界为 0x001D7800，差额 **-1576 B**。该报告可能来自历史失败构建，不能用于确认目前固件安全。原断言只比较 `__StackLimit >= __HeapLimit`，在分离堆布局中比较的是两个不同区域，不能独立证明 DRAM 数据未覆盖主栈。本次增加静态数据/主栈断言，以及 D_HEAP 起止地址检查。

host-wifi 的旧脚本使用 80/84 KiB 堆，不能直接套用四路池的预算；使用下述专用 profile。勿随意打开 DPD/FLASH_FW/HIB 后沿用上述地址和余量：不同模式内存布局不同，HIB 还只有两个固件 STA 槽，新应用会拒绝编译该模式。普通 AIC8800M40 固件的 NX_REMOTE_STA_MAX 为 8，已容纳四台，无需修改固件 ABI 的站点数组大小。

## 构建和验证

### AIC8800M40 接收缓冲复核（2026-09-10）

按当前 `target_btdm_wifi2` / `host-wb`、DPD=off、非 FLASH_FW 配置复核，40 ms/路的录音环可以保留，256 KiB 堆的地址范围符合该链接分支；该结论是预算判断，尚不是新固件链接及运行验证。

- 每路 PCM 接收环 7680 B，四路 30720 B；每路应用层重组区 1941 B，四路 7764 B。两者均已计入约 55392 B 的音频池，不能在池之外重复累计。
- 256 KiB 堆扣除音频池和三个音频任务的 43008 B 栈，预算剩余 163744 B，仍需承担当时已创建的系统任务、Wi-Fi/BT、互斥量、动态重排序副本和其他分配；该数不是运行时可用堆读数。
- `SO_RCVBUF=8192` 是每个共享 socket 的排队字节上限，不是每台 STA 独占 8 KiB，也不是启动时预先 malloc 8 KiB。录音只有一个共享 socket，邮箱深度 8。四台同时各送一帧最坏 1941 B 音频，共八片、7892 B UDP 载荷，能够装入空的 8 项/8192 B 队列，但已有积压或插入 HELLO 时仍可能丢包。它适合及时排空的低延迟接收，不宜把该队列当成额外 40 ms PCM 缓冲。
- `net_al.c` 使用 `pbuf_alloced_custom(..., PBUF_REF, ...)` 引用接收缓冲；不能将 UDP 队列载荷简单全部归到 lwIP 的 `MEM_SIZE` 中，也不能将 FreeRTOS 堆与 lwIP heap 混为一谈。
- 原 host-wb map 的 `HOST_RXBUF` 是 `0x108000..0x10FDFC`，占用 32252 B / 32768 B，剩余 **516 B**，来自 `libwifi_apsta.a(rwnx_utils.o)`。当前未扩大这块底层数组，所以应用环扩大不会直接撑破该区；该区不具备把底层接收槽数简单翻倍的空间。实际新库的布局必须重新查看新 map。
- `rwnx_rx.c` 的乱序路径还会通过 `rtos_malloc` 复制整块 `fhost_rx_buf_tag` 和 `recv_msdu`。当前源码限制全局待重排帧为 6，剩余堆低于 12 KiB 时走释放/旁路处理。该限制不是每台设备 6 帧；若链接使用旧预编译 Wi-Fi 库，需要核实库中实现是否与源码一致。

建议保留当前应用录音环与 UDP 队列设置，先获取新 map 和四路满负载的 `UACM HEAP` 最小剩余值；不要因芯片型号相同就套用 `map_cm4_wifi.txt`、DPD 或 FLASH_FW 的另一套地址，也不要在未核对底层库和地址相邻区域前扩充 HOST_RXBUF。

在原 SDK 的 Linux、Python 2、ARM GCC 9.2.1 构建环境中，从项目根目录运行：

```sh
sh config/aic8800m40/target_btdm_wifi2/build_udp4.sh
python3 tools/check_uac_map.py build/host-wb-aic8800m40/linkinfo.armgcc_4_8.txt
```

该入口固定 SOFTAP=on、DPD=off、USB_DEVICE=on、HEAP_SIZE=0x40000；target_btdm_wifi2 原构建脚本的堆默认值也已同步改为 0x40000。不要通过 `-libuse` 复用含旧应用/旧 lwIP 配置的库，首次应在原 SDK 环境完整重编译。只检查构建成功且时间更新后的 map，避免把历史报告当作本次结果。

主机可运行：

```sh
python tests/run_uac_udp4.py
python tests/check_uac_syntax.py
```

第一项直接提取生产源码中的 codec、混音和 UDP 分发函数进行测试，覆盖四个单独输入、四路满幅归一化、安静输入回退、静音、压缩往返/CRC损坏/原始回退、分片边界/乱序/重复/超时/序号回绕、四端注册、第五 ID 拒绝、重复 HELLO、端点/token 绑定、独立方向超时和重连。socket/时钟为确定性 mock，不代表 lwIP 或射频实测。第二项用 SDK 头文件及主机 32 位 GCC 做语法检查，有 Windows errno 与嵌入式 lwIP 定义差异的日志；不替代 ARM 编译链接。

上板验收至少包括四台同时播放+录音、分别断开/重启任意设备、反复开关 USB 流、丢包/乱序注入、满幅四路输入、长时间运行以及堆/任务栈最低水位。检查客户端均收到正确 ID 的播放、T3/T4 确实参与混音，掉线一台不阻塞其余三台，CRC 错误不会输出坏 PCM。CPU 是否满足每 5 ms 混音周期、射频吞吐和实际时延，需要实测后定论。
